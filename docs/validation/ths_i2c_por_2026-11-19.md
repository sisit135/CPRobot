# THS early I2C detection and live POR investigation

## Scope and result

Tested on the connected STM32F411CE, device ID `0x10006431`, through ST-Link.
Both physical buses responded before sensor device HAL initialization. The
captured failure was narrower than a whole bus failing: main-bus address
`0x29`, configured as TCS34725, acknowledged GPIO probes but NACKed normal
STM32 controller address probes. LSM303DLHC addresses continued to acknowledge
on that same controller. This investigation does **not** establish a fix for
the reported intermittent POR regression or identify the electrical cause.

The diagnostic trace build blocks all application services and motion. The
deployed image includes the existing local motor nSLEEP override to PB13;
that unrelated working-tree change is not part of the I2C commit. Settings
sectors 6/7 were preserved byte-for-byte across programming.

## Startup change

BUP now performs the following work before motor, settings and sensor device
HAL initialization:

1. Validate the configured isolated bus wiring.
2. Enable GPIO clocks with SDA/SCL as inputs and record line levels.
3. Probe both buses with an open-drain GPIO master, before either
   `Wire.begin()`, without register reads, address assignment or XSHUT changes.
4. Initialize and inventory the hardware controllers independently, recording
   line levels, controller status and reset flags.

Both GPIO inventories execute even when one bus is stuck. GPIO clock stretching
is bounded to 1 ms; outputs are always released. Device HAL startup reuses the
prepared buses. Additional snapshots follow motor/settings startup and IMU/ToF
initialization. Existing device health gates remain authoritative.

The GPIO probes do not issue recovery pulses. The Arduino core's subsequent
`Wire.begin()` retains its existing recovery behavior. The extra probes add
startup time and can change the timing of an intermittent fault; they are
diagnostic instrumentation, not evidence of POR reliability.

## Live observations

A full-system power cycle of the previous image was captured first. Its early
hardware scan showed I2C1 `0x19` and `0x1e` ACK, I2C1 `0x29` no ACK, and I2C2
boot address `0x29` ACK. Thus both controllers responded on that baseline boot.

The initial instrumented image was then programmed and verified, followed by
a software-reset boot and a user-operated full-system power cycle. The latter
reported `RCC.CSR=0x0e000000` (POR/BOR/pin flags, without software-reset flag).
Reset flags were read without clearing; warm reset flags can accumulate.

| Probe | Software-reset boot | Full-system POR |
| --- | --- | --- |
| GPIO main `0x19`, `0x1e` | ACK | ACK |
| GPIO main `0x29` | ACK | ACK |
| GPIO ToF | Assigned `0x30`/`0x31`/`0x32` ACK, sensors retained power | Boot `0x29` ACK, assigned addresses absent |
| Hardware I2C1 `0x19`, `0x1e` | ACK | ACK |
| Hardware I2C1 `0x29` | No ACK | No ACK |
| Hardware I2C2 | Assigned addresses ACK | Table not retained during SWD reconnection |

The POR temporarily disconnected SWD; restarting RTT collection recovered the
buffered early inventories. Later records exceeded the 2048-byte RTT ring and
cannot be reconstructed. A shared boot-address ACK cannot identify/count ToFs;
an ACK at main `0x29` alone does not establish TCS identity.

On the instrumented software-reset boot, controller snapshots were unchanged
across initializing the other controller and across motor/settings HALs:

```text
SDA=1 SCL=1
CR1=0001 CR2=0030 SR1=0000 SR2=0000
state=20 error=00000000 CCR=00f0 TRISE=31
```

TCS setup subsequently failed with `id=0x00`. This was a failed read, not a
verified identity value.

## Controlled debugger experiments

Subsequent experiments used software resets, not PORs. A breakpoint at the
first HAL probe of main address `0x29` showed a valid READY handle, unlocked,
100 kHz configuration, no prior error, and an idle controller. Inspecting the
address phase **before HAL cleared flags** gave `SR1=0x0400` (AF/NACK), with
state BUSY. HAL returned `HAL_ERROR`, restored READY/unlocked state and left
`ErrorCode=0`. The failure was an address NACK, not a stuck BUSY flag.

| Controlled change for that probe | Result |
| --- | --- |
| Normal 100 kHz transaction | `HAL_ERROR`, AF/NACK |
| CCR=960 / 25 kHz | `HAL_ERROR` |
| Digital filter=15 APB cycles | `HAL_ERROR` |
| PB6/PB7 GPIO slew set low | `HAL_ERROR` |
| Breakpoint pause after START/SB, before writing the address to DR | `HAL_OK` at 100 kHz |

Debugger-controlled address transactions with longer software pacing also
acknowledged `0x29` at multiple clock rates. These observations identify
transaction-pacing sensitivity; they do not prove a silicon erratum, a required
sensor delay, a power fault, or a particular pull-up/wiring defect. Debugger
pauses can themselves change slave state. No delay/filter/slew workaround was
added to production. Final deployment resets these temporary register changes.
The next discriminating measurement is an SDA/SCL waveform around START,
address `0x52`, and ACK/NACK, compared with GPIO probing.

## Validation and retained evidence

The 14 focused native checks passed: BUP success/failure ordering and gates,
diagnostic startup, Arduino sensor HAL, and address diagnostics. GPIO checks
decode all 112 write addresses, ACK sampling, START/STOP, stuck SDA handling,
bounded clock stretching and final pin release. Native fixtures cannot validate
electrical timing. Trace and production profiles compile/link successfully;
the final trace image was deployed and verified. See [building](../building.md)
for canonical build commands.

The final software-reset capture again showed all three main GPIO responders,
LSM ACKs and main `0x29` no ACK through hardware, all assigned ToFs ACKing,
and TCS setup failing at `id=0x00`. Services remained skipped. Persistent
settings matched the pre-update backup. The final trace binary is 236728 bytes,
SHA-256 `4b784bbcc4675198b4010a233c8d80238b5e36723ce6f41718e806abfb100226`.
The final input-mode GPIO-clock preparation correction was verified on this
software-reset boot; the instrumented POR above preceded that correction.

These local files are temporary evidence, not repository fixtures or a
navigation/full-system qualification. EKF and navigation behavior were not
changed or requalified in this investigation.
